# 0009: ALTER DATABASE CONNECTION LIMIT fallback for PostgreSQL < 16

## Decision

`connectionLockdown` auto-selects its locking mechanism from the
configured `services.postgresql.package` version, with no option
surface change: PostgreSQL 16+ keeps the `pg_hba.conf` mechanism
(ADR 0007); PostgreSQL < 16 uses a new `ConnectionLimitLockdownManager`
(`src/collation_guard/lockdown.py`) that locks a database via
`ALTER DATABASE ... CONNECTION LIMIT 0` instead. `connectionLockdown.enable`
stays default `true` on every version -- the version only changes
*how* it's implemented, never whether it's on by default.

## Why this exists: a production incident, not a hypothetical

`include_if_exists` -- the `pg_hba.conf` directive ADR 0007's whole
mechanism depends on -- was added in PostgreSQL 16, not before
(confirmed against the release notes:
https://www.postgresql.org/docs/16/release-16.html#RELEASE-16-PG-HBA,
"Allow include files in pg_hba.conf and pg_ident.conf ... controlled by
`include`, `include_if_exists`, and `include_dir`"). The module
injected that directive unconditionally, regardless of the configured
PostgreSQL version. On a PostgreSQL 15 deployment, every single startup
hit `FATAL: could not load pg_hba.conf` / `invalid connection type
"include_if_exists"` and crash-looped forever, since the same broken
line was regenerated by this module on every boot -- a real server
(`postgresql.service` permanently `failed`) running PostgreSQL 15.19,
confirmed via its own startup log, is what surfaced this. A sibling
server running PostgreSQL 16.15 was unaffected -- same module, purely
version-dependent.

## Two options considered, not one

**Disable `connectionLockdown` by default on PostgreSQL < 16, warn
about the gap.** Implemented first, then explicitly rejected by review:
closing the server-03 crash-loop by silently dropping a documented
correctness guarantee (ADR 0007's entire reason for existing) is a
regression dressed up as a fix, even with a loud `warnings` entry
explaining why. "Never silently off" was the explicit bar -- a
`nixos-rebuild build` warning is a mitigation for an unavoidable gap,
not a substitute for actually closing it when a substitute mechanism
exists.

**A different mechanism for the versions that can't use
`include_if_exists`.** `CONNECTION LIMIT` was ADR 0007's own
previously-rejected alternative to `pg_hba.conf` -- rejected there as
the *primary* mechanism specifically because superuser connections are
exempt from it. That gap doesn't go away here; it's accepted
explicitly as a fallback, not reintroduced by accident:

- `CONNECTION LIMIT` is enforced server-side, synchronously, with no
  config-file reload lag (unlike `pg_hba.conf`'s `pg_reload_conf()` +
  `pg_conf_load_time()` confirmation dance in ADR 0007's own
  `_reload_and_confirm()`) -- `ALTER DATABASE ... CONNECTION LIMIT 0`
  takes effect the instant the statement commits.
- It rejects every *non-superuser* connection attempt, which is real
  protection against the exact gap ADR 0007 names: "a cron job, a
  manually-run `psql`, a service with only `Wants=postgresql`" -- none
  of those are superuser by default.
- It does **not** reject a superuser connection
  (https://www.postgresql.org/docs/17/sql-createdatabase.html,
  `CONNECTION LIMIT` notes: "the limit is not enforced against
  superusers or background worker processes") -- a real, standing,
  *documented* narrowing relative to the `pg_hba.conf` mechanism, not a
  bug. Surfaced on every `nixos-rebuild build`/`switch` via NixOS's own
  `warnings` mechanism (`nixosModule/config.nix`), not buried in this
  file alone.

Weaker-but-real protection, chosen over a correctness guarantee that
was never actually enforceable on these PostgreSQL versions in the
first place.

## Restoring the original limit, not a hardcoded `-1`

Unlike ADR 0007's `pg_hba.conf` file (which simply doesn't exist when
nothing is locked), a database's `CONNECTION LIMIT` is a persistent
property of that database (`pg_database.datconnlimit`) that can
already carry a deployment's own deliberately-configured value before
this guard ever touches it. `ConnectionLimitLockdownManager` queries
and records the *actual* value in-memory (and in the crash-recovery
state file, see below) before locking, and restores exactly that value
on unlock -- not a blanket `-1` (unlimited), which would silently
clobber a pre-existing custom limit on every single run.

## A state file for crash recovery, not the pg_hba.conf file's "delete-first" pattern

ADR 0007's `cleanup_lockdown_file()` deletes its file *before*
attempting to reconnect/reload, because the file's mere presence is
itself the dangerous state -- deleting it is the safety action,
independent of whether the follow-up reload succeeds (the next
`postgresql.service` start reads a fresh `pg_hba.conf` regardless).

That property doesn't hold here. The dangerous state (a database's
live `CONNECTION LIMIT`) lives *inside the already-running cluster*,
not on disk -- the JSON state file
(`/var/lib/postgresql-collation-guard/connection-limit-lockdown.json`,
`dbname -> original limit`) is only a record of what to restore, not
the thing that needs restoring. `cleanup_connection_limit_lockdown()`
therefore only deletes it *after* successfully reconnecting and
restoring every entry -- if Postgres itself is unreachable (the
scenario that most often triggers this cleanup at all, per
`run_on_failure`'s own docstring), the file is left in place so a
later invocation can still retry against it, rather than silently
discarding the only record of what needed fixing.

Written atomically (temp file + `os.replace`, same directory): a torn
write here isn't an inert extra `pg_hba.conf` rule Postgres parses
permissively (ADR 0007's file), it's JSON this project's own
crash-recovery code must successfully parse -- a process killed
mid-write must never leave a corrupt file behind.

## `/var/lib`, not `/run` -- and a self-heal that doesn't wait for `OnFailure=`

The state file deliberately does **not** live under
`/run/postgresql-collation-guard` alongside `lockdownFile`/`contextFile`
(both tmpfs, wiped on every reboot). For those two, that's exactly
correct: `lockdownFile`'s only effect is its own existence (no file ->
`include_if_exists` silently no-ops -- a reboot IS the recovery), and
`contextFile` is diagnostic-only. Neither has state living anywhere
else that a reboot could orphan.

This file is different. The *dangerous* state -- a database's live
`CONNECTION LIMIT` -- is real, durable Postgres catalog data
(`pg_database.datconnlimit`) that survives a reboot on its own, with
or without this file. If the file lived on tmpfs too, a genuine
machine-level crash (power loss, kernel panic -- nothing graceful
enough for `OnFailure=` to ever fire at all, since the whole machine
is gone, not just this one process) would wipe the *only record* of
what to restore, on the exact same reboot that leaves the live
database stuck at `CONNECTION LIMIT 0` forever -- a silent, permanent
lockout with no automated recovery path. So `connectionLimitStateFile`
is placed under `/var/lib/postgresql-collation-guard` instead (a
`systemd.tmpfiles.rules` `d` entry, which only ensures the directory
exists with the right permissions -- unlike `D`/`e` it never touches
existing *contents*, so a file already sitting there from before a
reboot survives untouched).

That alone isn't sufficient, though: surviving the reboot only helps
if something actually *reads* it afterward. `run_on_failure()` (the
`OnFailure=` companion unit) is necessarily silent on this exact
machine-level-crash path, since nothing runs it. The fix:
`main.run()` itself now calls both `cleanup_lockdown_file()` and
`cleanup_connection_limit_lockdown()` unconditionally, before doing
any new work, on *every single invocation* --
`_cleanup_stale_lockdown_state()`. The main guard unit is guaranteed to
run on every boot, before `postgresql-setup.service`/`postgresql.target`
(`before = ["postgresql-setup.service"]`), so this is the one place
certain to run after any crash, graceful or not -- not a substitute for
`run_on_failure`'s own cleanup (which still fires faster, immediately
after a process-level failure that doesn't take the whole machine
down), but the backstop for the one scenario that skips it entirely.

**Honest test-coverage limit:** this project's own nixosTest suite uses
the systemd-nspawn container backend (ADR 0005). A genuine
power-loss/crash simulation was actually attempted here -- not just
assumed impossible -- via `os.kill(machine.process.pid, 9)` against
the test driver's own `systemd-nspawn` subprocess, then
`wait_for_shutdown()` + `start()` against the same root directory.
Confirmed, via `findmnt` and systemd's own `InvocationID`, that this
does *not* actually restart the container for this backend -- see
`docs/learnings/nspawn-crash-simulation.md` for the full investigation
and why it wasn't worth chasing further.
`tests/nixos/pg15-connection-limit-fallback.nix` instead verifies the
wiring this guarantee depends on --
`COLLATION_GUARD_CONNECTION_LIMIT_STATE_FILE` actually resolves to a
`/var/lib/...` path on the real systemd unit -- and the fast Python
tier (`tests/test_main.py`) proves `_cleanup_stale_lockdown_state()`'s
own behavior directly (a stale state file present at the top of
`run()` gets restored before any new work starts, exactly reproducing
what a crash leaves behind, with no container reboot needed to do so).
What's *not* independently proven end-to-end in this repository is
`/var/lib` itself surviving an actual reboot while `/run` doesn't --
that rests on the standard, well-established NixOS/systemd filesystem
convention (`/var/lib` is persistent state storage; `/run` is tmpfs),
not a project-specific behavior.

## Both cleanups always run, unconditionally and independently

`run_on_failure` (the `--on-failure` companion unit's entry point) now
unconditionally attempts *both* `cleanup_lockdown_file()` and
`cleanup_connection_limit_lockdown()`, regardless of which mechanism
the main run was actually configured with. Each is already a no-op
when its own path is `None` or its own file doesn't exist (the common
case), so the companion unit never needs to know which mechanism was
selected -- simpler, and robust against any future env-var drift
between the main unit and its on-failure companion.

## Same single-writer-thread shape as LockdownManager

`ConnectionLimitLockdownManager` mirrors `LockdownManager`'s
`_submit()`/`_run()`/`_drain_with_error()` shape exactly (same FIFO
queue of `lock`/`unlock` requests processed by one dedicated thread,
same atomic error-check-then-enqueue race closed the same way) -- see
ADR 0007's "Single-writer thread, not per-worker file access" for the
full reasoning, not repeated here. The termination sweep
(`pg_terminate_backend` excluding `application_name = 'collation-guard'`)
is also identical -- `CONNECTION LIMIT` alone only blocks *new*
connection attempts, so an already-open session still needs explicit
termination, same as the `pg_hba.conf` mechanism.
